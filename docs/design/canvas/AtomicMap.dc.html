EL MAPA
De átomo a pantalla

Atomic design se inventó para la web, donde una página es un archivo. En Android hay módulos Gradle, ViewModels y navegación, así que las cinco capas hay que traducirlas. Esta lámina es esa traducción: qué capa es qué cosa en Kotlin, dónde vive el archivo y qué le está permitido importar.

EL CORTE
Las tres primeras capas viven en el design system y no saben que existe FakeStore. Las dos últimas viven en la feature y sí. Esa línea entre organismo y plantilla es la única frontera que importa: por encima de ella todo se puede previsualizar sin levantar la app.

03 — LA REGLA

Las flechas van en un solo sentido

app
NavHost, tema raíz
feature:products
ViewModels, plantillas, mappers
core:designsystem
átomos, moléculas, organismos
nada del proyecto
solo Compose y M3
Por qué ProductCard puede vivir en el design system
Porque no recibe Product sino ProductCardUiModel, un data class que el propio módulo declara: id, título, precio, url de imagen, categoría, rating. La feature traduce de dominio a modelo de UI en su mapper.
GANO
El árbol atómico completo queda en un módulo que compila y se previsualiza sin la app. Los previews no necesitan Hilt ni red.
PAGO
Un modelo espejo y un mapper por pantalla. Si cambia el dominio hay que tocar dos archivos, no uno.
SI NO
En una app de una sola feature, mover ProductCard a feature:products y dejar el DS solo con piezas genéricas también es correcto, y ahorra el mapper.
Cómo se verifica que la regla se cumple
Una regla que solo vive en un documento se rompe en la tercera semana. En Gradle esto es comprobable: core:designsystem simplemente no declara a domain ni a ninguna feature en sus dependencias, así que el import ni siquiera compila.
// core/designsystem/build.gradle.kts
dependencies {
  implementation(platform(libs.androidx.compose.bom))
  implementation(libs.androidx.compose.material3)
  implementation(libs.androidx.compose.ui)
  // nada de :domain, nada de :feature
}
El día que alguien intente importar Product dentro de un átomo, la compilación se cae. Eso es la regla, no el README.
04 — EL PAR

Route y Screen

Partir cada pantalla en dos es lo que hace testeable a la app. La plantilla no puede llamar al ViewModel porque no lo tiene; la página no puede dibujar porque no sabe cómo.

ProductListRoute
PAGINA
@Composable
fun ProductListRoute(
  onProductClick: (Int) -> Unit,
  vm: ProductListViewModel = hiltViewModel(),
) {
  val state by vm.uiState
    .collectAsStateWithLifecycle()
  ProductListScreen(
    state = state,
    onProductClick = onProductClick,
    onFavoriteClick = vm::toggleFavorite,
    onRetry = vm::refresh,
  )
}
No se testea con Compose: no hay nada que afirmar. Se prueba el ViewModel por separado.
ProductListScreen
PLANTILLA
@Composable
fun ProductListScreen(
  state: ProductListUiState,
  onProductClick: (Int) -> Unit,
  onFavoriteClick: (Int) -> Unit,
  onRetry: () -> Unit,
) {
  Scaffold(topBar = { FsTopBar(…) }) {
    FsStateHost(state) { content ->
      ProductGrid(content.items, …)
    }
  }
}
